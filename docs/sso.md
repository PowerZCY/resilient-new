# SSO 登录系统设计方案

## 1. 背景与目标

当前系统仅支持基于硬编码配置的账号密码登录。为了提升用户体验、扩展用户来源并增强系统安全性，需要将现有登录系统升级改造为支持多种认证方式的单点登录（SSO）系统。

**目标:**

*   支持用户名/密码、邮箱、多种第三方账号登录。
*   支持新用户通过邮箱或第三方账号注册。
*   用户凭证和信息存储于数据库。
*   UI 风格现代化，参考提供的设计截图。
*   集成第三方认证开放平台以简化多提供商对接。

## 2. UI 设计

新的登录/注册页面 UI 设计将参考用户提供的截图风格，保持简洁、现代的美感。

*   **登录页:**
    *   包含用户名/邮箱输入框、密码输入框。
    *   提供 "记住我" 选项。
    *   显著的 "登录" 按钮。
    *   在表单下方或侧边提供清晰的第三方登录选项图标按钮（例如 Google, GitHub, WeChat 等）。
    *   提供 "忘记密码？" 和 "还没有账号？注册" 的链接。
*   **注册页:**
    *   提供邮箱注册表单（邮箱、密码、确认密码）。
    *   同样提供第三方账号注册的选项。
    *   包含服务条款和隐私政策的链接及同意选项。
*   **整体风格:** 采用截图中的渐变色按钮、圆角卡片和清晰的版式布局。

## 3. 认证流程

### 3.1. 用户注册

#### 3.1.1. 邮箱注册

1.  用户访问注册页面，选择邮箱注册。
2.  输入邮箱地址、设置密码并确认。
3.  同意服务条款和隐私政策。
4.  点击 "注册"。
5.  系统校验邮箱格式和密码强度，检查邮箱是否已被注册。
6.  若校验通过，在 `users` 表中创建新用户记录（初始状态可设为 "待验证"）。
7.  生成邮箱验证令牌，发送验证邮件到用户邮箱。
8.  用户点击邮件中的验证链接。
9.  系统验证令牌有效性，并将用户状态更新为 "已验证" 或 "激活"。

#### 3.1.2. 第三方账号注册

1.  用户访问注册或登录页面，选择一个第三方提供商（如 Google）。
2.  系统重定向用户到该第三方提供商的授权页面。
3.  用户在第三方平台登录并授权本应用访问其基本信息（如用户ID, 邮箱, 昵称）。
4.  第三方平台通过回调 URL 将授权码（Authorization Code）或令牌（Token）返回给本系统。
5.  系统后端使用授权码向第三方平台换取访问令牌（Access Token）和用户信息。
6.  系统检查该第三方账号是否已关联现有用户（通过 `provider_name` 和 `provider_user_id` 在 `user_third_party_accounts` 表中查找）。
    *   **如果未关联:**
        *   检查获取到的邮箱是否已在本系统注册：
            *   如果邮箱已存在，提示用户该邮箱已注册，建议其登录后在用户中心绑定第三方账号。
            *   如果邮箱不存在或第三方平台未提供邮箱，系统在 `users` 表创建新用户记录（可使用第三方昵称作为初始用户名，状态为 "已验证"）。
        *   在 `user_third_party_accounts` 表中创建关联记录，存储 `user_id`, `provider_name`, `provider_user_id` 以及获取到的令牌信息（可选）。
    *   **如果已关联:** 直接进入登录流程（见 3.2.3）。
7.  用户注册成功并自动登录。

### 3.2. 用户登录

#### 3.2.1. 账号密码登录

1.  用户在登录页面输入用户名（或邮箱）和密码。
2.  点击 "登录"。
3.  系统后端查询 `users` 表，根据用户名或邮箱查找用户。
4.  若找到用户，校验输入的密码和数据库中存储的哈希密码是否匹配。
5.  若匹配成功，生成会话（Session）或 JWT（JSON Web Token），返回给前端，用户登录成功。
6.  若用户勾选 "记住我"，可以延长会话有效期或使用长期有效的 Refresh Token。

#### 3.2.2. 邮箱登录

流程与账号密码登录类似，用户在用户名输入框中输入邮箱地址即可。后端逻辑需同时支持用户名和邮箱查询。

#### 3.2.3. 第三方账号登录

1.  用户在登录页面点击一个第三方提供商图标。
2.  系统重定向用户到第三方授权页面（如果用户之前未授权或授权已过期）。
3.  用户在第三方平台登录并授权。
4.  第三方平台通过回调 URL 返回授权码或令牌。
5.  系统后端换取访问令牌和用户信息。
6.  系统使用 `provider_name` 和 `provider_user_id` 在 `user_third_party_accounts` 表中查找关联的本地用户 `user_id`。
    *   **如果找到关联用户:**
        *   查询 `users` 表获取用户信息。
        *   生成会话或 JWT，用户登录成功。
    *   **如果未找到关联用户:**
        *   检查获取到的邮箱是否已在本系统注册：
            *   如果邮箱已存在，提示用户该邮箱已注册，建议其使用邮箱/密码登录后在用户中心绑定此第三方账号。
            *   如果邮箱不存在或未提供，引导用户进入一个简化的注册流程（可能需要补充用户名或确认信息），然后创建新用户和关联记录（类似 3.1.2）。
        *   或者，直接拒绝登录，提示用户需要先注册或绑定账号。具体策略根据产品需求决定。

## 4. 数据库设计

需要设计两张核心表：用户信息表和第三方账号关联表。

### 4.1. `users` 表

存储用户的核心信息。

| 字段名          | 类型          | 约束/索引        | 描述                                   |
| --------------- | ------------- | -------------- | -------------------------------------- |
| `id`            | BIGINT / UUID | PRIMARY KEY    | 用户唯一标识符                         |
| `username`      | VARCHAR(50)   | UNIQUE, INDEX  | 用户名（可选，如果允许邮箱登录则可为空） |
| `email`         | VARCHAR(255)  | UNIQUE, INDEX  | 邮箱地址                               |
| `email_verified`| BOOLEAN       | DEFAULT FALSE  | 邮箱是否已验证                         |
| `password_hash` | VARCHAR(255)  |                | 哈希后的密码（使用 bcrypt 等强算法）     |
| `display_name`  | VARCHAR(100)  | NULLABLE       | 显示昵称                               |
| `avatar_url`    | VARCHAR(512)  | NULLABLE       | 头像 URL                               |
| `status`        | VARCHAR(20)   | DEFAULT 'active'| 用户状态 (active, inactive, pending_verification) |
| `created_at`    | TIMESTAMP     | NOT NULL       | 创建时间                               |
| `updated_at`    | TIMESTAMP     | NOT NULL       | 最后更新时间                           |
| ...             | ...           |                | 其他用户基础信息 (如手机号、简介等)    |

### 4.2. `user_third_party_accounts` 表

存储用户与第三方账号的关联信息。

| 字段名             | 类型          | 约束/索引                | 描述                                       |
| ------------------ | ------------- | ---------------------- | ------------------------------------------ |
| `id`               | BIGINT / UUID | PRIMARY KEY            | 关联记录唯一 ID                            |
| `user_id`          | BIGINT / UUID | FOREIGN KEY (users.id) | 关联的本地用户 ID                          |
| `provider_name`    | VARCHAR(50)   | NOT NULL, INDEX        | 第三方提供商名称 (e.g., 'google', 'github') |
| `provider_user_id` | VARCHAR(255)  | NOT NULL, INDEX        | 用户在第三方平台的唯一标识符               |
| `access_token`     | TEXT          | NULLABLE               | 第三方访问令牌 (加密存储)                  |
| `refresh_token`    | TEXT          | NULLABLE               | 第三方刷新令牌 (加密存储)                  |
| `expires_at`       | TIMESTAMP     | NULLABLE               | `access_token` 的过期时间                  |
| `provider_data`    | JSON / TEXT   | NULLABLE               | 从第三方获取的原始用户信息（可选）         |
| `created_at`       | TIMESTAMP     | NOT NULL               | 关联创建时间                               |
| `updated_at`       | TIMESTAMP     | NOT NULL               | 关联更新时间                               |

**索引:**

*   在 `user_third_party_accounts` 表上创建 `(provider_name, provider_user_id)` 的复合唯一索引，用于快速查找用户是否已通过特定第三方账号关联。
*   在 `user_id` 上创建索引，方便查询用户绑定的所有第三方账号。

## 5. 第三方登录开放平台集成

为了简化对接多个第三方登录提供商（如 Google, Facebook, GitHub, Apple, 微信, QQ 等）的复杂性（不同的 OAuth/OpenID Connect 实现细节），推荐集成一个身份认证即服务（IDaaS）平台或使用成熟的开源库/框架。

**推荐选项:**

1.  **Auth0 / Okta:**
    *   **优点:** 功能强大，支持众多开箱即用的社交和企业级身份提供商，提供统一的 API 和管理界面，安全性高，文档完善，有免费套餐（通常有用户数限制）。
    *   **缺点:** 对于大规模用户或高级功能可能成本较高，数据存储在第三方平台。
2.  **Keycloak (开源):**
    *   **优点:** 开源免费，功能全面，支持 OAuth 2.0, OpenID Connect, SAML，可自托管，完全掌控数据和配置，社区活跃。
    *   **缺点:** 需要自行部署、维护和扩展，相比商业服务需要更多运维投入。
3.  **云服务商方案 (AWS Cognito, Google Identity Platform, Azure AD B2C):**
    *   **优点:** 与各自的云生态系统深度集成，通常有慷慨的免费额度，扩展性好。
    *   **缺点:** 可能存在一定的厂商锁定风险，配置相对 Auth0 可能稍复杂。
4.  **Passport.js (Node.js 生态):**
    *   **优点:** 如果后端是 Node.js，这是非常流行的认证中间件，拥有大量第三方策略（Strategies），灵活度高。
    *   **缺点:** 需要自行整合和管理用户数据库、UI 等，更偏向于库而非完整平台。

**选择建议:**

*   如果预算允许，追求快速上线和易用性，**Auth0** 是一个优秀的选择。
*   如果希望完全掌控并有能力进行自托管和运维，**Keycloak** 是强大的开源替代方案。
*   如果已经深度使用某个云平台，其对应的身份服务（**Cognito/Identity Platform/Azure AD B2C**）值得考虑。

集成这些平台后，本系统后端主要负责处理平台回调、管理用户数据库（创建用户、关联账号）以及生成自己的会话/JWT，而与各个第三方提供商的具体协议交互则由所选平台处理。

## 6. 安全考虑

*   **密码存储:** 必须使用强哈希算法（如 bcrypt, Argon2）存储密码，并加盐（Salt）。
*   **令牌处理:**
    *   第三方 `access_token` 和 `refresh_token` 如果需要存储，必须加密。
    *   本系统生成的 JWT 或会话 ID 应具有合理的过期时间，并考虑使用 Refresh Token 机制。
    *   启用 HTTPS 保护所有通信。
*   **OAuth/OIDC 安全:**
    *   使用 `state` 参数防止 CSRF 攻击。
    *   严格校验回调 URL。
    *   保护好第三方应用的 Client ID 和 Client Secret。
*   **输入验证:** 对所有用户输入进行严格验证，防止 XSS、SQL 注入等攻击。
*   **速率限制:** 对登录、注册、密码重置等接口实施速率限制，防止暴力破解。
*   **邮箱验证:** 强制要求邮箱验证，确保邮箱所有权。

## 7. 迁移计划

1.  **数据库准备:** 创建 `users` 和 `user_third_party_accounts` 表结构。
2.  **数据迁移:**
    *   编写脚本，将现有硬编码的用户名和密码（假设存在）迁移到 `users` 表。
    *   在迁移过程中，对原始密码（如果以明文或弱哈希存储）使用强哈希算法进行处理。
    *   标记这些迁移过来的用户状态，可能需要引导他们在首次登录后验证邮箱或设置更强的密码。
3.  **功能上线:** 部署新的登录/注册逻辑和 UI。
4.  **旧逻辑移除:** 在确认新系统稳定运行后，移除旧的硬编码登录逻辑。

## 8. API 设计 (初步)

需要设计以下 API 端点：

*   `POST /api/auth/register/email`: 邮箱注册
*   `POST /api/auth/login/password`: 用户名/密码/邮箱登录
*   `GET /api/auth/providers/{provider}`: 重定向到第三方授权页
*   `GET /api/auth/providers/{provider}/callback`: 处理第三方回调
*   `POST /api/auth/logout`: 用户登出
*   `POST /api/auth/password/forgot`: 发起密码重置请求
*   `POST /api/auth/password/reset`: 处理密码重置
*   `GET /api/auth/verify/email`: 处理邮箱验证链接
*   `GET /api/users/me`: 获取当前登录用户信息
*   `POST /api/users/me/link/{provider}`: 用户登录后绑定第三方账号
*   `DELETE /api/users/me/link/{provider}`: 用户解绑第三方账号
